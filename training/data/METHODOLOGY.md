# Fine-tuning dataset methodology

**Task:** natural-language project description → valid `ProjectSchema` JSON
(see `src/types/project-schema.ts`). This document exists from the first
commit — including while the dataset is 12 pairs, not 500 — because the
splits, the validation rule, and the reasoning behind them are exactly what a
much later reader (or a future session doing synthetic generation) needs and
cannot recover from the data alone.

## Storage format

One JSONL file per source, one JSON object per line:

```json
{"prompt": "...", "schema": { ... ProjectSchema ... }, "source": "hand-written", "sourceUrl": "..."}
```

- `prompt` — the natural-language input, verbatim.
- `schema` — a `ProjectSchema` object. Every pair in this repository has been
  run through the real `validateProjectSchema` (`src/workflow/validate-project-schema.ts`)
  before being committed — see `training/data/validate-dataset.mjs`.
- `source` — one of `hand-written`, `real-project`, `synthetic`. Never inferred,
  always set explicitly when the pair is written.
- `sourceUrl` — optional. Set for `real-project` pairs (link to the repository
  or issue the description was drawn from); omitted for the other two sources.

## Three sources, and why they are not interchangeable

| Source | What it is | Target count |
|---|---|---|
| `hand-written` | Written by a person, one at a time, deliberately covering a spread of prompt styles (well-specified, ambiguous, terse, unusual architecture) | **80** |
| `real-project` | Descriptions drawn from real repositories/issues, schema constructed to match what was actually built | **120** |
| `synthetic` | Model-generated prompt/schema pairs, produced once a first fine-tune exists to bootstrap from | **300** |

Total target: **500 pairs**.

## The hard rule: validation draws from `hand-written` only

**`training/data/gold/` holds only the `hand-written` split, and it is the
only source ever used for validation/held-out evaluation. `real-project` and
`synthetic` pairs are never written into `gold/`, at any point, regardless of
how good a synthetic pair looks.**

This is enforced **structurally**, not by a field someone could forget to
filter on:

- `hand-written` pairs live in their own directory, `training/data/gold/`.
- `real-project` and `synthetic` pairs will live in sibling directories —
  `training/data/real-project/` and `training/data/synthetic/` — created when
  those sources actually start being collected. Nothing is pre-created empty
  here; an empty placeholder directory is a place a stray file quietly lands.
- Any training/eval split logic reads `gold/*.jsonl` for validation and
  everything else for training, by directory, not by reading a `source` field
  out of a merged file. A directory boundary has to be actively crossed to
  violate this; a field has to merely be forgotten.

**Why this matters enough to enforce structurally:** a synthetic pair is
generated by the same kind of model being fine-tuned. If synthetic data ever
leaked into the validation split, validation would start measuring the
model's ability to imitate its own prior output rather than its ability to
produce a correct `ProjectSchema` from a genuinely novel prompt — the eval
number would look better and mean less, with no way to tell from the number
alone that this had happened. Keeping `real-project` out of `gold/` too is
the more subtle case: a `real-project` pair's schema was constructed by a
person looking at what was actually built, which is a different (easier)
task than generating a schema from a prompt with no ground truth to check
against — mixing it into validation would optimistically bias the eval score
in the same direction, just less obviously.

## Validation

Every pair, from every source, is validated the same way, by
`training/data/validate-dataset.mjs`:

1. The envelope (`prompt` non-empty, `source` one of the three literals,
   `sourceUrl` a string if present) is checked by
   `validateDatasetPair` (`src/workflow/dataset.ts`).
2. The `schema` field is checked by the real `validateProjectSchema` —
   the same function used everywhere else in this repository, not a
   parallel or looser check for dataset purposes.
3. A pair that fails either check is reported with its specific reason(s)
   (JSON path + reason code) and the run exits non-zero. **A failing pair is
   never silently dropped and never silently kept** — both are a kind of
   data corruption that is easy to introduce quietly and expensive to notice
   later.

Run it with:

```bash
npm run build:server   # validate-dataset.mjs imports compiled output, like scripts/*.mjs already do
node training/data/validate-dataset.mjs
```

## Near-duplicate detection

The same script computes Jaccard similarity (word-set overlap, after
lowercasing/punctuation-stripping/whitespace-collapsing — see
`normalizePrompt` in `src/workflow/dataset.ts`) between every pair of
prompts and flags any pair at or above a threshold (default 0.8, override
with `--dup-threshold=`). This is a warning, not a hard rejection: a
near-duplicate prompt is a signal to look at the pair, not automatically a
mistake (two genuinely different projects can be described in very similar
words). It exists so the dataset's effective size — how much distinct signal
80, 120, or 300 pairs actually represents — doesn't quietly inflate from
copy-paste-and-tweak authoring, which is the natural failure mode of writing
many similar prompts by hand.

## Current state

12 `hand-written` pairs exist in `training/data/gold/gold.jsonl`, written as
a proof of the format (see the commit that introduces this file for the
count and a rejection report — all 12 passed on generation). This is a
deliberate checkpoint, not the finished 80: writing all 80 in one sitting
risks the same repetitive-phrasing problem the dedup check exists to catch,
so the remaining ~68 are written in later sessions, checked against
`validate-dataset.mjs` incrementally rather than as one large unreviewed
batch.

`real-project` and `synthetic` collection has not started. `synthetic`
specifically should not start until a first fine-tune exists to generate
from — see [[project_loq_no_7b_model]] for the machine constraint that
applies once that fine-tuning work begins in earnest (LOQ rehearses on the
0.5B model only; the real training run happens on the borrowed desktop).
