# Held-out generalization eval — run_20260912_154324 replaces baseline

**Checkpoint:** `run_20260912_154324` (base Qwen2.5-7B-Instruct + LoRA adapter,
`r=16, lora_alpha=16, learning_rate=2e-4`, **3 epochs**, **288 training rows**,
final training loss 0.7309, peak VRAM 9.37GB — trained on the borrowed desktop
via `train_full.py`; see `training/runs/run_20260912_154324/summary.json`).

**This checkpoint is now the default in `local_inference_server.py` and
`src/llm/local.ts`'s `DEFAULT_LOCAL_MODEL`, replacing the original baseline**
(`run_20260822_130636`, 91 rows). `RESULTS.md` and `RESULTS-CONFIG-C.md`
document the baseline and the rejected Config C run respectively; this
document is the delta on top of both, and the reasoning for why this one
replaces baseline despite tying it on the two numbers that eval was built
around.

## Training config, and why it's identical to baseline's LoRA hyperparameters

`r=16`, `lora_alpha=16`, `epochs=3`, `lr=2e-4`, batch_size=2, no dropout —
confirmed by reading `train_full.py` directly (baseline's own `summary.json`
never recorded LoRA hyperparameters at all, only Config C's did; this was a
metadata gap, not evidence the values differed). Per Config C's own finding —
more epochs traded away held-out correctness for a lower training-loss number
that didn't hold up under inspection — this run deliberately did **not**
increase epochs or rank. The only variable changed was training-data size:
91 rows → **288 rows**, via `training/data/synthetic/synthetic-batch-2.jsonl`
(185 pairs merged from a 197-prompt real-pipeline capture batch) plus the
already-existing `synthetic-batch-1.jsonl` (12 pairs), on top of the
unchanged `gold`/`real-project` splits.

## Methodology note: every number below uses the SAME verified pipeline

Unlike `RESULTS.md`/`RESULTS-CONFIG-C.md`'s original scoring (bare
`JSON.parse` + `validateProjectSchema`, no repair, no id-rewrite —
`validate-holdout-outputs.mjs`), every number in this document — for
baseline, Config C, and this checkpoint alike — was re-derived by re-running
each checkpoint's already-captured raw generation text through the real
`createProjectSchemaGenerator`/`finalize()` pipeline: both JSON-repair
functions (including the `repairPrematureDependsOnElement` fix from this same
session) and the unconditional `rewriteComponentIds`/`rewriteConstraintIds`
id recomputation every real production call already goes through. This is a
deliberate, disclosed change in methodology, not a like-for-like reuse of the
old published numbers — see the comparison table below for both readings.

Held-out pass count under the *original* (bare-validator, no repair, no
id-rewrite) methodology moves the baseline's published number from 8/10 to

touched (repair fired 0 times across all 30 baseline+ConfigC+new held-out

or `repairMissingComponentsArrayClose` signatures).

**On these two numbers, this checkpoint does not improve on baseline.**
Training loss is lower (0.7309 vs 0.9032) but this is not a clean
comparison — the dataset size changed 3.16x, not just epoch count held
constant — and Config C already demonstrated lower training loss does not
predict better held-out behavior. The fake-id defect is structural (the
model cannot compute a real SHA-256 by predicting tokens, per `RESULTS.md`'s
root-cause section) and is exactly as present here as in baseline — more
data did not, and was never expected to, fix it.

## The actual question this dataset effort exists to answer: constraint generation

This is the axis synthetic-data collection was undertaken to fix.
`LOCAL-MODEL-CONSTRAINT-ROOTCAUSE-PROBE.md` found the original 91-row
training set was **73.6% empty-constraint** (67/91 rows) and that both the
baseline and Config C checkpoints produced **0/10 constraint-bearing
outputs** on the held-out set — a complete failure to generate constraint
content at all, regardless of whether the prompt called for one.

**Training-data composition, after the merge:** the new 288-row
`training/formatted/dataset.jsonl` is **26.7% empty-constraint** (77/288) —
73.3% now carry at least one constraint. The imbalance did not just
improve, it inverted.

**Held-out behavior — checked directly, not inferred from the data shift:**

| Checkpoint | Held-out outputs with ≥1 constraint (original 10-prompt set) |
|---|---|
| Baseline | 0/10 |
| Config C | 0/10 |
| **New checkpoint** | **4/10** |

A small sample (4 constraint-bearing outputs) is not enough to size the
quality of those constraints, so a second, independent, 18-prompt probe set
was built specifically to test this — multi-domain, explicit cross-domain
access-control language, checked for zero near-duplicates against the full
training corpus and the original held-out set before running. Every
generated `rawText` was checked word-by-word against its source prompt for
invented detail (a number, a named rule, a restriction not stated anywhere).

**Constraint-quality probe result (n=18, new checkpoint only):**

| | Count | Rate |
|---|---|---|
| Grounded (rawText restates only what the prompt stated) | 17/18 | 94.4% |
| Confabulated (rawText adds unstated specific detail) | 1/18 | 5.6% |
| Empty (no constraint where one plausibly should exist) | 0/18 | 0% |

The single confabulation (a HOA voting app) added "residents can only see
their own vote" — a plausible but unstated inference, not a fabricated
number or named rule; nothing in this larger sample resembled the earlier
4-example set's more concerning inventions (e.g., "no automated matching or
pool lending is supported," stated nowhere in that prompt). **The earlier
4-example sample's 2/4 confabulation rate did not replicate at real sample
size — it was noise, not signal.**

## Why this checkpoint replaces baseline despite tying it on pass-count and fake-id rate

Held-out pass count and the fake-id defect are the metrics `RESULTS.md`'s
original eval methodology was built around, and this checkpoint is flat
against baseline on both — stated plainly, not softened. If those were the
only axes this project cared about, the honest conclusion would be "no
measurable improvement despite 3.16x the data."

They are not the only axis. The original, stated reason synthetic-data
collection started at all was the 73.6% empty-constraint skew diagnosed in
`LOCAL-MODEL-CONSTRAINT-ROOTCAUSE-PROBE.md` — a checkpoint that structurally
could not produce constraint content regardless of what the prompt asked
for. Baseline and Config C both score **0/10** on that axis. This checkpoint
scores **4/10** on the same set and, at a real sample size built to test it
specifically, **17/18 grounded** with **zero empty** outputs on a
constraint-worthy prompt set. That is a direct, measured fix to the problem
this entire effort exists to solve, with no measured regression on any other
axis (pass-count, fake-id rate, or repetition artifacts — none appeared in
either held-out set under this checkpoint).

**Decision: `run_20260912_154324` replaces `run_20260822_130636` as the
default checkpoint** in `local_inference_server.py`'s `--model-name` default
and `src/llm/local.ts`'s `DEFAULT_LOCAL_MODEL`. The original baseline
checkpoint directory (`training/runs/run_20260822_130636/`) is retained,
unmodified, for future comparison.

## Open items, not closed by this checkpoint

- **The fake-id defect is unfixed and, per `RESULTS.md`'s own root-cause
  analysis, is not fixable by more training data** — the recommended fix
  remains architectural: have the calling orchestrator recompute ids via
  the real `componentId()` rather than trust the model's output. Production
  already does this (`rewriteComponentIds` in `finalize()`); this checkpoint
  changes nothing about that necessity.
- **Memorized `sessionId` persists unchanged** — same real training
  sessionIds recur regardless of the held-out prompt's actual content, same
  bookkeeping-not-judgment issue `RESULTS.md` identified for baseline.
- **The one real confabulation found (5.6% rate, n=18)** is a small but
  non-zero risk worth re-checking at a larger sample before treating this as
  fully closed — 18 is large enough to show the earlier 2/4 was noise, not
  large enough to put a tight confidence interval on the true rate.
